# V3.3.3 - profiles, friends, recovery and themed waiting states

Base: V3.3.2 `493a81c8e6a3765a2615ed1339c5b236e2d91b05`. The accepted theme pack (`src/styles.css`), icon adapter, game rules, Elo/coin formulas, tournament formats and payouts are not redesigned.

## Guest -> linked profile -> recovery

Guest is the default optional entry, not an auto-registered Google/Apple account. Offline bot and pass-and-play work without sign-in. Free one-device/LAN parties keep their existing behavior. Guest progress is saved locally; uninstall/cleared storage or a new device cannot recover it without a prior linked cloud backup. Signing in is required for persistent online identity/friends and server play.

The startup shows the chosen theme's nine-cell board animation while session/save state is actually loading. No fake progress percentage or deliberate extra wait is inserted. A landing page offers Google, Apple and Continue as guest. Unconfigured providers are unavailable; guest play remains usable. No provider password is collected by Mega XO.

Web Google uses authorization code + PKCE, state and nonce. Apple uses a code-only request with no personal-name/email scopes, allowing a query callback. Native identity endpoints accept an SDK ID token bound to a server-issued nonce. Both routes verify signatures, issuer, exact audience, expiry, issued-at, nonce and provider subject. The server uses an allowlisted JWKS endpoint and algorithm, not a token-supplied URL.

An identity is `(provider, sub)`; email never merges or restores profiles. Linking a second provider to the existing actor preserves tag, username, friends, online wallet/rank and saves. Linking an identity already owned by another actor returns an explicit conflict. No balance sums or quiet account replacement occur. Recent authentication is required for sensitive link/unlink changes. The Linked accounts screen provides a Verify again action for existing providers; this reauthentication is bound to the current actor and rejects a different Google/Apple identity without switching or merging profiles. The last linked login cannot be removed. Sessions rotate after sign-in/link and can be signed out on one or all devices.

## Profile contract

- Permanent internal actor ID and permanent globally unique `MEGA-...` tag, generated/checked by the server. Existing server friend codes are preserved when unique.
- Unique normalized username: 3-20 lowercase ASCII letters/numbers/underscores, starts with a letter. Usernames are case-insensitive, reserved names are rejected and changes have a 7-day cooldown after the first choice.
- Separate 28-character display name and six built-in avatar glyphs.
- Server Elo, league and statistics remain attached to the actor, not the username.
- Copy tag, native/browser share where supported, and `#player=<tag>` links reopen a profile after sign-in.
- Editable stats visibility (public/friends/private) and presence visibility (friends/hidden).

Search is authenticated, bounded and rate-limited: exact tag or username prefix of at least three characters, at most 20 results. Blocked/held profiles are not intentionally exposed. Search does not return private stats, provider subjects or email addresses.

## Friends and challenge flow

Preserve the old Friends page structure, adding clickable profile rows. Search -> Add -> recipient accepts -> mutual friendship -> click profile -> see allowed Ranked/Casual/Friends statistics -> Challenge (1v1). Incoming/sent friend requests have accept/decline/cancel actions; removing/blocking clears the graph and open invitations. Reciprocal requests are cleared on both sides once either is accepted; held profiles are not exposed by search/profile reads. Tags can be searched, copied and shared.

Profile statistics come from server-completed match history. They show games, wins, win rate, average time, hours and draws by mode. Editable offline practice archives are not published as competitive achievements. Own offline bot statistics remain on the existing Stats page.

Free challenges are available immediately to linked friends; paid/rated challenges retain the previously approved placement, eligibility, amount, mutual consent and settlement rules. A client cannot label a stranger as a friend to use friend pricing. The server checks friendship again at acceptance. The actual existing game board, moves, turn timers, results and stats pipeline are reused, not replaced with a new mock board.

## Presence

Authenticated per-session heartbeat every 15 seconds; lease expires after 45 seconds. Foreground -> Online; background -> Away; expired/logged-out session -> Offline. Multiple devices are aggregated; one foreground device keeps the player online. In-match, queued and in-lobby status are derived from server game/queue/room records, not client-provided strings. Presence is visible to mutual friends by default. Hidden status remains hidden. A network cut is not detected instantaneously; it settles within the lease window.

## Progress and conflict handling

Local practice snapshots are backed up under the signed-in actor with a monotonically increasing revision. Save uses compare-and-swap; a second device with a stale revision gets `SAVE_CONFLICT` instead of overwriting a newer save. On first linkage or profile switching, existing practice saves are deliberately chosen, not silently combined. The displaced device snapshot is archived on that device. Offline changes retry when connected, including after a cold restart without a network session. The device retains the owner and last cloud revision of pending changes. A newly created second profile also requires an explicit choice before importing practice from a previously linked profile; starting fresh does not silently copy the previous account. Restored guest unfinished bot/local matches are rebuilt through legal moves before resuming.

Online Coins/Crowns, purchases, rank, ranked/casual/friend history and friends live in the authoritative SQLite economy/profile stores. Cloud practice includes the old local wallet as untrusted practice state for same-profile restoration, but no account balance or competitive result is read from it. Linking does not turn edited offline Coins into spendable online currency. A verified offline-reward promotion pipeline remains a separate future feature.

## Waiting UX

Four renderings of a lightweight CSS board motif: Vector route pulse, Midnight soft signal glow, Paper ink/highlighter drawing and After Hours stepped arcade cells/segmented loading track. The accepted palettes/typefaces/materials remain the source of truth. No new generated videos/images, fake queue counts, fake success states or fake percent complete are used.

The existing queue sheet opens immediately, shows elapsed waiting, can cancel, handles match-found acceptance/expiry and then enters the existing match. Friend invitations show themed waiting-for-acceptance. Lobby waiting displays the actual roster/ready counts. Reduced-motion users get a static but legible state; animation is not required to understand readiness.

## Running and configuration

`npm run start:accounts` starts the same-origin Node service with one shared SQLite path. Static hosting alone supports guest UI but not server identity/friends/cloud saves. Copy `.env.example` to deployment secrets (the server reads environment variables, not a dotenv file automatically). Use Node >=22.13. Set MEGA_ORIGIN to the exact HTTPS public origin and register the exact Google/Apple callback URLs. In local development only, loopback HTTP is permitted. Native SDK adapters/contracts live under `native/`; they are not compiled applications.

The combined service mounts `/api/account`, `/api/community`, `/api/v1` and `/api/party` with the same authenticated actor. HttpOnly, SameSite=Lax, Secure-in-HTTPS cookies; CSRF token and exact Origin on mutation; bounded bodies, request limits and safe static path allowlists. No provider client secrets or identity subjects enter public profile JSON. The native finish verifies real signed tokens; test signing keys/endpoints are test-only.

A deployment can inject `networkContext(req,actor)` with trusted edge measurements for the accepted matchmaker. Never take latency/region from client JSON. Queue tickets are single-process ephemeral state; running multiple matchmakers requires a shared scheduler/lock service, not just another instance of this reference server.

Paid operation remains off by default. Configuring identity does not activate payments or remove existing platform/jurisdiction checks.

## Known release boundaries

- Real Google/Apple credentials, app registrations, HTTPS origin and actual user-consent flows are not provisioned in this branch.
- Kotlin/Swift adapter source is provided, but an Android/iOS app target, bridge, SDK dependencies, signing and physical-device validation are still required.
- Provider revocation notifications, full account-deletion workflow/retention policy and native store release requirements need review before shipping.
- Security-sensitive auth code should receive independent review and provider interoperability tests, not be considered audited because regression tests pass.
- Cloud save is a versioned profile backup, not a monetary merge. Server deployment/backups remain operational responsibilities.
