# V3.5 monetisation implementation and release contract

This addendum is authoritative for V3.5 monetisation. V3.4's competitive currency, Elo, season, tournament and fairness rules remain unchanged. The research and reasons for selecting/rejecting particular techniques are in [V3.5-MONETISATION-RESEARCH.md](V3.5-MONETISATION-RESEARCH.md).

## Delivered in the repository

The shared policy, browser UI, SQLite accounting, HTTP integration, ECDSA rewarded-ad verification, product grants, restore/refund handling, tests and sensitivity model are implemented. The app has a permanent **Rewards & Style** entry on Home and Quests and from Wallet/Settings, not an extra advertising-only bottom-navigation tab. It contains actual decorative previews and equip controls, free earning information, optional rewards, clear purchase summaries and restore/privacy/report controls.

Live inventory, real native billing and device privacy management are **not provisioned**. No fake ad or payment is substituted. The default server has ads and purchases disabled; a missing native bridge leaves the relevant controls unavailable. The test providers exist only under `tests/`.

### Exact initial policy

Automatic interstitials need every condition: second or later app session, 24 hours since first seen on the installation, five completed meaningful bot games overall, three since the last automatic ad, eight accumulated active-play minutes, and eight wall-clock minutes since any full-screen ad. Caps are two per session and six per UTC day. They are considered only at **normal bot result -> Home**, never on Rematch, during a turn, on app open/exit, or in tutorial/local/online/queue/party/tournament/forfeit flows. A newly completed bot record must exist, so an old record cannot cause an ad after practice or an aborted game.

The server independently enforces account age, daily cap, full-screen cooldown, current activity and Remove Ads ownership. The browser rechecks context after obtaining a short-lived permit; a slow permit or navigation during the request cancels presentation. A permit is not an impression. Conservative permits may consume a cap even if presentation fails: do not report them as ad revenue.

Optional rewards require a separate review and explicit Watch action. One completed, verified ad gives **5 Cosmetic Credits**, or activates **2x free Casual cosmetic earnings for ten minutes**. Games started inside the window may finish later. Four shared ad **starts** per UTC day, minimum two-minute spacing. A start reserves an opportunity even if skipped or failed; the review explains this. Counting starts, rather than only completed callbacks, prevents expired tickets and delayed callbacks bypassing the cap. Pending boosts cannot be stacked or replaced by another unresolved boost request.

Cosmetic Credits are not purchasable, transferable, exchangeable, stakeable or included in wealth/Elo. Free Casual queue completions earn 2 credits, capped at 10/day. A boost adds at most 10/day. Only server-qualified normal line/draw results count, not client-posted results. Claiming previously uncollected server history is supported with the historical completion day's cap; duplicate matches never pay twice. Exact match start is taken from the persisted authority match when available, with the existing elapsed-time record as a legacy fallback.

The maximum repeatable cosmetic earning is 30/day with four fixed ads plus base play, or **35/day** with one boost, three fixed ads and sufficient qualifying play. Ad rewards mint **zero** competitive Coins and Crowns. Existing Copper/Orbit/Crown cosmetics bought with Coins remain recognized as owned.

## Server integration

Use `buildService()` from `server/community-server.js` with **trusted** `monetizationOptions`. Do not accept these options from an HTTP request, practice save or browser flag.

```js
const { buildService } = require('./server/community-server');
const { createAdMobVerifier } = require('./server/admob-ssv');

const service = buildService({
  file: databasePath,
  origin: configuredHttpsOrigin,
  // Existing verified identity/provider configuration is also required.
  monetizationOptions: {
    adMode: 'off', // Explicitly change to rewarded, hybrid or experiment after review.
    purchasesEnabled: false,
    adUnit: configuredRewardedAdUnit,
    rewardItem: 'cosmetic_reward',
    verifyAd: createAdMobVerifier(),
    eligible: account => approvedAudienceAndTerritory(account) === true,
    verifyPurchase: (evidence, actor) => verifyWithAppleOrGoogle(evidence, actor)
  }
});
```

The two named verification/eligibility functions are deployment dependencies, not implemented placeholder approvals. Default eligibility rejects unknown audiences. The server never accepts `watched: true`, `valid: true` or a client currency quantity as proof. `verifyPurchase` must authenticate the actual store transaction and app, product, owner binding, refund state, and store lifecycle. It returns `{valid, accountId, store, transactionId, productId, refunded}` only after verification. Proof checks happen before entering the synchronous SQLite write transaction; receipt ownership is checked again under the transaction.

The combined service routes the legacy `/api/v1/purchase` through the same new purchase gate, so the old path cannot bypass eligibility. The standalone old economy handler remains a reference interface and is not the recommended production assembly.

All player endpoints use the existing HttpOnly session, origin and CSRF guard, JSON-only bodies, bounded 16 KiB payloads and idempotency keys. Routes under `/api/monetization/` are `status` (GET), `claim`, `redeem`, `equip`, `purchase`, `restore`, `reward-ticket`, and `interstitial-permit` (POST). Client balances, winner, reward size, ad count and actor fields cannot replace the server values.

### Reward verification

Configure AdMob's rewarded unit for amount **1**, item **`cosmetic_reward`**. That means one server-defined choice, not a client-supplied number of credits. The server-issued ticket records whether the user selected fixed credits or a boost.

Configure the public SSV callback to `/api/monetization/admob-ssv`. This is the only route without player authentication; every callback must pass ECDSA verification over the original raw query, using Google's fixed HTTPS key endpoint. Key material is cached no longer than 24 hours. Duplicate query parameters, bad signatures, unknown keys, unexpected units/items/amounts, future/stale timestamps, another user's ticket, reused tickets and reused global provider transactions are rejected. Never configure callback data from the browser as already verified.

Tickets are usable for a signed completion within five minutes. Provider delivery may arrive up to 24 hours later. The persisted transaction makes duplicate delivery idempotent. A delayed, valid callback can grant the promised reward after the page closes; a boost starts when the verified grant arrives. No client completion callback grants credits. The user may see a pending verification message.

Back up the whole SQLite database, including the V3.5 tables, not just the original `state` row. Transaction deduplication, tickets and per-match cosmetic claims live in their own tables. The current snapshot architecture is not a throughput claim and still needs load testing.

## Native bridge contract

The source is a browser game with native adapter boundaries, not a compiled mobile project. The wrapper must implement real StoreKit/Play Billing, a real Google Mobile Ads SDK, CMP/UMP, audience settings, content ratings, lifecycle handling and applicable ATT flows before release.

`window.MegaBilling`:

- `products()` -> `Promise<Array<{id, price}>>`, where price is the real localized display price.
- `purchase(productId)` -> actual verified-store evidence. The native purchase sheet must require affirmative user confirmation. Persist unfinished transactions for retry; do not consume/finish them just because the SDK returns success.
- `acknowledge(evidence)` -> finish/acknowledge only after the server has accepted and recorded the grant. The UI calls this hook after successful verification.
- `restore()` -> evidence for restorable non-consumables. Consumable transaction recovery is a native/server lifecycle responsibility, not a new purchase or a device-local wallet import.

`window.MegaAds`:

- `privacyState()` -> synchronous current `{canRequestAds: boolean}` from the actual CMP/UMP/audience policy, not an inferred tracking permission.
- `privacyOptions()` -> opens the real privacy options flow. Declining personalized tracking must not penalize ordinary play or an otherwise permitted contextual ad reward.
- `prepare('rewarded' | 'interstitial')` -> preload only when permitted. It must not show an ad.
- `isReady(format)` -> synchronous true only for a loaded creative that can present immediately.
- `showRewarded(ticket)` -> set SSV `user_id=ticket.actor` and `custom_data=ticket.ticket`, use `ticket.adUnit`, then immediately present the loaded creative. The returned completion result is informational only.
- `showInterstitial()` -> immediately present a loaded creative, or skip. Never load and unexpectedly display later over a new match.
- `reportAd()` -> a real reporting/ad-inspection surface.

Native presentation must pause/resume audio appropriately and never obscure a live game because an asynchronous SDK loader finished late. SDK-owned close controls and ad timing remain provider behavior. The app does not promise a universally fixed ad duration. Configure ad pods and creatives deliberately and test on physical devices. Never use live inventory in automated tests.

## Analytics and experimentation

`MonetizationStore.report()` provides aggregate server events for requests, verified rewards, cosmetic grants/redemptions, verified purchases/restores/refunds, and automatic permits. It is a trusted server method, not an exposed player report. These records are **not a substitute** for SDK impression-level revenue, fill, retention and session telemetry. Provider impression/revenue export and a production analytics pipeline remain deployment work.

`tests/monetization-model.js` emits `.artifacts/v35-monetization-model.json` with low/base/high assumptions for 10,000 DAU, net IAP after assumed fees/refunds, ad contribution, and Remove Ads break-even. These are sensitivity scenarios, not observed results. Never treat the V3.4 90-day modeled purchaser share as a daily purchase rate.

Keep a no-ad control, assign by account, and analyze all assigned users rather than comparing only viewers with non-viewers. Begin with rewarded-only testing before enabling hybrid. Predeclare the observation window and retention margin, estimate sample size from beta baselines, and evaluate net revenue alongside D1/D7 retention, qualified play, ad exits, refund rate and crashes. Do not raise ad frequency after a loss, failed purchase or refusal to watch.
