# V3.5.1 validation evidence and limits

Baseline: V3.5 `6a17bca67003a825de86c85a2875efcec7f11288`. V3.5.1 adds first-party email/password accounts, clearer self-profile access and the archived board-frame direction while retaining V3.5 ad cadence and the V3.4 competitive economy.

## Automated validation contract

`.github/workflows/v35-validation.yml` runs on both V3.5 and V3.5.1 and executes:

1. source checkpoint;
2. full Node regression — `npm test`;
3. game-design invariants — `npm run test:invariants`;
4. Ranked balance report;
5. 5,000-player / 90-day economy model;
6. monetisation sensitivity model;
7. Chromium monetisation/account flows;
8. retained logs, model reports and screenshots.

A validation pass during V3.5.1 development on the corrected email UI wiring produced:
- **230 tests / 230 pass / 0 fail** in the full Node suite;
- **15 tests / 15 pass / 0 fail** in the design-invariant suite;
- Ranked balance passed;
- population economy model passed;
- monetisation sensitivity model passed;
- Chromium V3.5.1 account/monetisation flow passed;
- validation artifact upload succeeded.

The final branch head must still be judged by the workflow attached to that exact SHA; an earlier green or partially superseded run is never treated as proof for later changes.

## Email/password account coverage

The new account tests cover:
- email normalization to lowercase;
- syntactic email validation;
- duplicate normalized-email rejection;
- password minimum rules;
- salted scrypt password hashing rather than plaintext storage;
- wrong-password and unknown-account failures returning the same generic credential error;
- signup creating the same authoritative profile/account model used by Google/Apple;
- signin restoring the same actor, stable player tag and edited username;
- linking email/password to an existing Google/Apple profile;
- unlinking email while another recovery method remains;
- recent email reauthentication before sensitive identity changes;
- real HTTP signup/signin using the existing HttpOnly session, origin and CSRF protections;
- cloud-practice-save recovery across a second browser/client session.

The targeted account command includes these tests:

`npm run test:accounts`

### What email tests do not establish

The source validates email **syntax**, not ownership of the mailbox. There is no production transactional-email service, verification link/code delivery or password-reset delivery in this branch. Those remain production account-release gates.

## Profile/UI coverage

The Chromium flow uses the real HTML/JS/CSS, HTTP handlers and SQLite stores with isolated test providers at native billing/ad boundaries.

The V3.5.1 flow verifies:
- email signup from the landing screen;
- self-profile opening after account creation;
- username/display-name editing;
- the Friends page exposing **View / edit your profile**;
- Cosmetic Credit balance shown in Rewards & Themes;
- no board-frame gallery or frame purchase surface;
- the archived-board-collection notice;
- responsive Rewards & Themes layouts across the four retained themes at 320, 390 and 768 pixels;
- a signed rewarded-ad callback granting 5 account-bound Cosmetic Credits without changing Coins/Crowns;
- the same Cosmetic Credit balance shown on the self profile;
- absence of `starter_100` and `style_collection` purchase controls;
- Crown-pack and Remove Ads purchase confirmation;
- restore preserving Remove Ads without duplicating consumable Crowns.

The browser harness inlines unchanged repository assets because direct loopback browser navigation is restricted in the validation environment, then bridges browser requests to the real local Node service with a per-browser cookie jar.

## Monetisation/economy invariants retained

V3.5.1 does not change:
- Elo inputs;
- Ranked rewards/fees;
- public tournament economy;
- season qualification;
- automatic-ad cadence;
- rewarded-ad quotas;
- Cosmetic Credit non-transferability;
- the rule that ad rewards mint zero competitive Coins/Crowns.

The frame catalogue is archived. Cosmetic Credits are banked for future themes and currently have no player spend endpoint.

## Production gates still open

Automated correctness does not establish production readiness for identity or monetisation. Remaining work includes:
- real mailbox ownership verification;
- password-reset/recovery email delivery;
- email deliverability/rate-limit/abuse operations;
- real native Apple/Google billing adapters and receipt lifecycle;
- live ad SDK/provider configuration;
- trusted age/territory/privacy controls;
- physical-device lifecycle and accessibility checks;
- deployment/load/backups and production analytics;
- beta retention/monetisation evidence;
- the separate paid-entry compliance gate.

No live advertisements, real purchases or production emails are used by the automated test providers.
