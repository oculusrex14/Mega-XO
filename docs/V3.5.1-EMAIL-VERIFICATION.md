# Mega XO email verification and recovery

V3.5.1 uses verified email ownership for every first-party email identity. Mega XO is developed by **Antimatter Innovations** and production transactional email is sent from:

**Mega XO by Antimatter Innovations <contact@antimatterinnovations.com>**

The mailbox/domain is owned by Antimatter Innovations, but owning the mailbox alone does not authorize API delivery. The sending domain must also be verified with the transactional-email provider.

## Production provider

The current adapter uses **Resend** over its HTTPS email API. No SDK dependency is required; Node 22's built-in `fetch` is used.

Required production environment variables:

- `RESEND_API_KEY` — server-only Resend API key.
- `MEGA_EMAIL_FROM` — optional override; defaults to `Mega XO by Antimatter Innovations <contact@antimatterinnovations.com>`.
- `MEGA_OTP_SECRET` — a long random server secret used to HMAC OTP values before they are stored.

Never expose these variables to browser JavaScript or commit them to Git.

## Domain setup

Before production sending:

1. Add `antimatterinnovations.com` to the Antimatter Innovations Resend account.
2. Add the DNS records Resend displays for the domain. The sending setup currently requires the provider's SPF and DKIM records; use the exact values from the dashboard rather than copying examples from documentation.
3. Complete domain verification in Resend.
4. Keep the existing `contact@antimatterinnovations.com` mailbox active so users can reply/contact the developer.
5. Configure DMARC for the parent domain as part of production email hardening. Start with an appropriate monitoring policy and tighten it after verifying legitimate senders.
6. Set the production environment variables above and restart the account service.
7. Perform a real-device verification and password-reset test before launch.

## Account creation flow

The landing screen has one **Continue with email** action.

For an already verified account:
1. normalize the email;
2. validate the password;
3. sign into the existing profile.

For a new email:
1. validate the email and proposed password;
2. create a pending OTP challenge only — no player account is activated yet;
3. send the OTP to the submitted mailbox;
4. require the user to enter the code;
5. only after a valid code, create the authoritative Mega XO account, email credential, profile and session.

A legacy V3.5.1 email credential with no recorded ownership verification is treated as unverified and must pass OTP verification before it can be used again.

## OTP security policy

- 6 numeric digits generated with Node's cryptographic RNG.
- 10-minute validity.
- Single use.
- Bound to the browser session, normalized email and purpose.
- Stored only as an HMAC, never as plaintext.
- Maximum 5 incorrect attempts for one challenge.
- Minimum 60 seconds before another code can be requested for the same flow.
- Per-session and per-email hourly rate limits.
- Superseded challenges are invalidated.
- Expired challenges cannot activate an account or reset a password.

The email contains the purpose, code, expiry notice and Antimatter Innovations developer identity. It does not contain the user's password.

## Forgot password

The **Forgot password?** flow reuses the OTP system:

1. user submits an email;
2. the UI receives the same generic response whether or not that address exists;
3. if a matching email credential exists, the server sends a reset OTP;
4. OTP verification creates a limited reset authorization;
5. the user sets and confirms a new password;
6. the server replaces the salted scrypt password hash;
7. all previously signed-in sessions for that account are revoked;
8. the current browser receives a fresh session;
9. a password-changed notification is sent to the verified mailbox.

A nonexistent account receives no email, but the public response shape remains the same to reduce account-enumeration leakage.

## Password storage

Passwords are not stored or emailed in plaintext. Mega XO uses a random per-password salt and Node's `scrypt` password derivation. The OTP secret is independent from password salts.

## Automated tests

Automated tests never call live Resend or send external email. They inject an isolated mail transport and assert:
- no account exists before signup OTP verification;
- real OTP verification creates the account;
- wrong/expired/reused codes fail;
- brute-force attempts persist and lock;
- verified existing email logins do not require another signup OTP;
- unverified legacy credentials do require OTP;
- linked email methods require ownership verification;
- forgot-password responses do not reveal account existence;
- reset OTP changes the password and revokes old sessions;
- the Resend adapter uses the Antimatter Innovations sender/branding;
- browser signup completes the OTP screen using the isolated test mailbox.
