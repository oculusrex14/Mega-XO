# V4.1 P1-9 security and abuse acceptance

Status: **repository implementation complete; live adversarial staging acceptance remains external**

P1-9 covers:

1. credential stuffing;
2. OTP abuse;
3. account enumeration;
4. purchase replay;
5. ad-reward replay;
6. challenge collusion;
7. tournament collusion;
8. leaderboard boosting;
9. bot/solver abuse.

The release principle is intentionally conservative: **protocol-invalid, replayed, forged, or rate-abusive actions may be rejected; behavioral heuristics only create review signals.** A fast or unusually strong legitimate player is not automatically blocked, suspended, de-ranked, or deprived of currency.

## Automated release gate

Run:

```bash
npm run abuse:audit
```

CI runs the same command on every V4.1 validation build.

The dedicated suite is:

- `tests/p1-abuse-acceptance.test.js`
- `tests/competitive-abuse.test.js`
- `tests/abuse-guard.test.js`

The full regression suite continues to cover the underlying account, matchmaking, economy, tournament and monetization invariants.

## 1. Credential stuffing

Implemented controls:

- production edge limits sensitive email-auth actions with persistent per-IP windows;
- production email authentication also limits a browser session and normalized email address;
- password verification uses the bounded asynchronous production password worker pool;
- raw IP addresses are not stored in the persistent abuse-limit key: the key uses an HMAC-derived pseudonym;
- high-value purchase/reward and queue/tournament churn paths have their own persistent budgets rather than sharing only a coarse request limit.

These controls reduce automated stuffing without locking normal gameplay moves behind a CAPTCHA.

## 2. OTP abuse

Implemented controls:

- six-digit OTP generated with cryptographic randomness;
- OTP bound to challenge ID, normalized email, purpose and browser session;
- 10-minute expiry;
- 60-second resend cooldown;
- five incorrect challenge attempts before lock;
- resend invalidates the older challenge and cancels superseded queued mail;
- successful reset invalidates other verified reset challenges through credential-version binding;
- OTP verification has independent session and edge budgets.

A code copied into a different browser session is not accepted.

## 3. Account enumeration

Production forgot-password behavior is deliberately existence-neutral:

- known and unknown addresses receive the same public response shape and message;
- both paths create an opaque challenge;
- an unknown account uses a dummy challenge and does not enqueue external mail;
- global outbox availability is checked before account existence is consulted;
- provider latency is not exposed in the HTTP response because delivery is asynchronous.

Public username/player search remains an intentional social feature and is separately rate-limited; it is not treated as a private email-account existence oracle.

## 4. Purchase replay

Store grants require trusted verification before the transaction enters the wallet transaction.

Replay defenses include:

- store + transaction ID identity;
- account binding;
- immutable product mapping;
- idempotency-key fingerprinting;
- duplicate transaction returns no second grant;
- the same transaction cannot be moved to another account;
- refund/revocation records prevent a previously revoked transaction from being restored;
- one-time products cannot be repeatedly restored as new purchases.

No client-supplied Crown quantity is trusted.

## 5. Rewarded-ad replay

Rewarded grants require:

- a server-issued ticket;
- exact account;
- exact reward kind;
- exact native platform/ad unit;
- bounded issue/expiry/callback timing;
- signed provider verification;
- unique provider transaction ID;
- exactly-once server transaction semantics.

Replaying the same provider event is idempotent and cannot grant the reward twice. Reusing the provider transaction against a different ticket is rejected.

## 6. Challenge collusion

Rated direct challenges keep the intended gameplay rules but limit easy win trading:

- one rated direct encounter per pair per rolling 24 hours;
- three per pair per UTC week;
- short rated direct outcomes receive `SHORT_DIRECT_RESULT_REVIEW`;
- unusually high direct pots retain `HIGH_VALUE_DIRECT_POT`;
- repeated rated-pair and repeated-forfeit patterns can add review signals.

These signals do **not** cancel a legitimate resignation or automatically alter Elo.

## 7. Tournament collusion

Public tournament matchmaking:

- refuses friend pairs in the same public cohort;
- respects mutual block relationships;
- keeps the 200-Elo hard cohort spread;
- prevents one account from entering more than one public queue/event at once.

Completed events are reviewed for:

- high overall forfeits;
- forfeits concentrated into one beneficiary;
- repeated pair forfeits;
- extreme automated move cadence.

Those are review flags only. Settlement still follows the deterministic tournament result unless an existing account hold/operator workflow is used.

## 8. Leaderboard boosting

Existing ranking defenses remain intact:

- players cannot choose a matchmade Ranked opponent;
- friends cannot be paired in Ranked queue;
- recent Ranked opponents are temporarily avoided;
- same-pair Ranked queue encounters are capped;
- direct rated pair frequency is capped;
- stake size never changes Elo K-factor or rating math;
- very short rated outcomes do not count toward season activity/requalification or weekly activity rewards;
- inactive players lose scarce published elite seats without deleting underlying Elo.

This makes simple resign farming much less useful while preserving the normal consequence that a real resignation can still lose rating.

## 9. Bot / solver abuse

The server remains authoritative for:

- whose turn it is;
- legal moves;
- revision order;
- clocks/timeouts;
- winner calculation;
- rating and wallet settlement.

A client cannot submit a winner, balance, rating delta, tournament placement, or forged result.

V4.1 also records **private server move-cadence evidence**. An extreme repeated sub-second pattern can add `AUTOMATION_SPEED_REVIEW` once a conservative sample threshold is reached.

Important:

- cadence evidence is not returned in ordinary match/tournament views;
- the heuristic does not auto-ban or alter results;
- no invasive device fingerprint was added;
- a sophisticated solver cannot be proven solely from move timing, so live telemetry and moderation evidence remain necessary.

## Operator workflow

Existing operator lookup now includes `competitiveRisk`:

- flagged standard matches;
- flagged public tournaments;
- review flags;
- server-side implicated actor IDs where available.

Private move-timing samples themselves are not returned by normal player views.

Operator suspension/hold/session-revocation remains an explicit, audited human action.

## Privacy / data minimization

P1-9 deliberately avoids adding a broad device fingerprinting system.

- persistent edge limiter keys contain HMAC pseudonyms, not raw client IPs;
- review timing metadata is server-private;
- no password, OTP, cookie, receipt secret or ad signature is written into abuse flags;
- heuristic flags are evidence for review, not an automated guilt label.

If stronger device/payment-link analysis is needed after launch telemetry, it should be designed as a separate privacy-reviewed change.

## Live acceptance still required

Repository tests cannot reproduce a real distributed attack, real mobile store callbacks, radio/network jitter, or human/solver behavior.

`EXT-36` tracks the final adversarial staging drill. It should include:

- credential stuffing from multiple controlled source addresses;
- OTP request/verify burst and resend tests;
- known/unknown recovery response comparison over real HTTPS;
- real purchase replay using Apple/Google sandbox evidence (also covered by EXT-22/23);
- real rewarded-ad callback replay (also covered by EXT-24);
- multi-account challenge/tournament win-trading attempts;
- queue rematch/leaderboard farming attempts;
- deliberately scripted fast-move client versus normal human/mobile latency;
- operator lookup of resulting review flags;
- confirmation that ordinary legitimate play is not blocked by the review heuristics.

Threshold tuning from this drill may change review sensitivity, but should not silently change core game/economy rules.
