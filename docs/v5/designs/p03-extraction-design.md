## 1. V5-03-01 - Consistent snapshot capture procedure

### 1.1 Production capture (reuse of the proven Restic pattern)

VERIFIED existing chain: operator-side `scripts/backup-run.js` validates the environment (`environment()`, `scripts/backup-run.js:6-13`: HTTPS S3 repository required, `RESTIC_PASSWORD_FILE` must exist, explicit `MEGA_BACKUP_BUDGET_BYTES`); `check` runs `restic check --read-data-subset=10%`; `retrieve <id>` requires an explicit hex snapshot id, refuses an existing target (`RESTORE_TARGET_EXISTS`) and restores into `/work/recovery-<id12>` then `backup.verify(file)` (`scripts/backup-run.js:26-30`); `once` runs `restic stats`, refuses to exceed the budget, and runs `restic backup --json --host <h> --tag mega-xo-v4 <mega.sqlite> <mega.sqlite.json>` (`scripts/backup-run.js:33-48`). The snapshot itself is produced by `snapshot(source,target)` in `server/production/backup.js:17-29`, which opens the source with `new DatabaseSync(source,{readOnly:true})` and copies it with the node:sqlite **online backup API** (`await backup(db,tmp)`), fsyncs the file and directory, and writes a manifest `{version:1,createdAt,sha256,bytes,schema}` where `sha256` is a streaming digest of the file (`digest()`, `server/production/backup.js:5`) and `schema` is the applied-migration count from `inspect()` (`server/production/migrations.js`). `verify()` (`server/production/backup.js:31-35`) rejects a manifest whose version/createdAt/bytes are not safe, whose byte length differs from the file, whose sha256 differs, or whose schema count differs. `restore()` (`server/production/backup.js:36-46`) requires explicit confirmation, snapshots the prior target, copies with `COPYFILE_EXCL`, re-runs `check` and moves any `-wal`/`-shm` aside.

DESIGN - P03 capture procedure (no production writer is touched; the writer-freeze requirement of `specs/01` section 2 belongs to the P22 cutover, and P03 consumes already-committed immutable snapshots):

**IMPLEMENTED** as `capture(sourcePath, snapshotPath, {captureClockMs?, sourceRelease?})` in `tools/v5-migration/capture.js`, exposed as `node tools/v5-migration/cli.js capture --source <db> --snapshot <file> [--capture-clock <ms>] [--release-sha <sha>] [--record <file>]`. Actual contract:

1. The copy is made with the SQLite online backup API through the existing, production-proven `snapshot()` in `server/production/backup.js` (WAL content included), never by copying the main file alone. That helper opens the source read-only and constructs no store.
2. Sensitive bytes never land in a shared directory: the copy is written into a fresh **0700** staging directory created before the first byte, at 0600 in WAL mode; it is normalized to `journal_mode=delete` inside that private directory, then moved to the destination, re-chmod 0600, and both the artifact and its directory are fsynced. The staging directory is removed in a `finally` even on failure.
3. The target is never overwritten: an existing target, its journal side files and its manifest are refused before any byte is written, and the name is reserved with an exclusive create before the finished artifact is renamed into place.
4. `captureClockMs` is either supplied or taken from the backup manifest's own `createdAt`; it is recorded (`clockSource`) without altering any source state. The source is opened read-only and is never checkpointed, journal-switched or otherwise modified (its sha256 before/after is recorded).
5. The finished artifact is validated by the extractor itself (`readSnapshot`): `quick_check`, `foreign_key_check`, the source-schema table/index/trigger inventory and every `v4_schema` checksum. Coverage is reported (not enforced) at capture; the coverage gate belongs to extraction.
6. The canonical destination is physically bound by `assertRawDestinationBound`: the ancestor chain is real-path resolved so a symlink alias cannot place raw production data in a Git checkout, a named published/CI artifact directory (`.git`, `.github`, `.artifacts`, `public`, `public_html`, `dist`, `coverage`) is refused even at mode 0700, and a world-readable destination directory is refused. There is no override flag.
7. No network, no provider call, no store/authority constructor. Source retrieval stays with the existing Restic tooling (points 1-4 of the original list), which this module only consumes as an already-retrieved local file.

Original procedure retained for the real production capture path:

1. `restic check --read-data-subset=10%` through the backup container (never `init`; the repository already exists and re-initializing it is forbidden by `docs/v5/ARCHITECTURE.md` and gated behind `--confirm-new-repository` in `scripts/backup-run.js:20`).
2. Select the snapshot by explicit full id; verify it was produced by the same release family being migrated and record `snapshot_completed_at` and the manifest `createdAt`.
3. `retrieve <snapshot_id>` into an isolated, non-serving target directory; the command already refuses an existing target and runs `backup.verify` on the restored file.
4. Independently recompute the file sha256 at extraction time (do not trust the stored manifest alone) and require equality with both the retrieved `<file>.json` manifest and the capture record.
5. Re-run the repository's own integrity tooling against the restored copy: reuse `scripts/db-maintenance.js` `integrity()` (`PRAGMA quick_check` must be exactly `ok`; `PRAGMA foreign_key_check` must return no rows) plus the raw-JSON validation pattern already used by `backup.check()` (`state` row present and `accounts`/`receipts`/`matches` parse as arrays; `server/production/backup.js:8-15`).
6. Enumerate `sqlite_master` for tables/indexes/triggers/views, read `v4_schema` rows and re-verify each checksum with the same `checksum(m)` function used by `server/production/migrations.js` (sha256 of `name + '\n' + sql`), and record `PRAGMA journal_mode`, `page_count`, `freelist_count`, `user_version`, `data_version` and per-table row counts.
7. Freeze the capture record: `capture_id`, `snapshot_id`, `file_sha256`, `bytes`, `manifest_createdAt` (this is the **capture clock**, section 3.3), `restic_check_result`, `integrity_check_result`, `foreign_key_violations`, `schema_head` (highest `v4_schema.id` = 8 on the verified snapshot) with per-migration checksums, and table/index/trigger/row-count inventory.
8. Drift proof (DESIGN): for a real final import, capture twice and require identical per-table hashes, or capture once while the writer is fenced; a single capture is only sufficient for fixture/dev work. Record `PRAGMA data_version` before and after enumeration.

### 1.2 Local dev-fixture equivalent (IMPLEMENTED)

The same code path is used against a disposable fixture database so that fixture captures and production captures are byte-comparable in structure: build the fixture DB (section 5), then call `capture()` (which internally uses `snapshot()` from `server/production/backup.js`) to obtain a WAL-safe single-file snapshot plus manifest; run `verify()` on it; then run the reader against the snapshot file, never against the live fixture file. Fixture captures live in a temp directory created with `fs.mkdtempSync` and are deleted afterwards. The capture clock is the fixture clock (or the fixture manifest's `createdAt`), which the fixture builder controls by injecting its clock.

**SOURCE CORRECTION (implemented).** `snapshot()` preserves the source's `journal_mode`, so a copy of a WAL fixture was itself a WAL file; a read-only open of that copy then created `-shm`/`-wal` side files next to it, and the copy's main-file hash could differ from the writer's. `capture()` therefore normalizes its OWN artifact to `journal_mode=delete` (a write to the copy only, never the source) inside its private 0700 staging directory, so the immutable snapshot carries no side file and a read-only open creates none. The reader refuses a WAL-mode file with `SNAPSHOT_JOURNAL_MODE_NOT_IMMUTABLE`, so a raw live database must be captured first.

The design prose below is retained; the implemented staging/normalization detail above supersedes its "temp directory" description.

### 1.3 Hashing of snapshot bytes, tables and actors (IMPLEMENTED; algorithm as specified)

- **Snapshot bytes**: streaming sha256 of the restored file (same algorithm as `digest()`, `server/production/backup.js:5`); recorded with byte length and the snapshot id.
- **Table content hash**: `table_hash(t) = sha256(name + '|' + row_count + '|' + join(sort(row_hashes)))` where `row_hash = sha256(canon(row))` and `canon` is the canonical serializer of section 3.1 with columns taken in sorted name order. Relational tables are semantically sets, so rows are sorted before aggregation (this is the "canonicalize ordering when hashing sets/maps" rule of `specs/01` section 5).
- **Per-actor canonical content hash**: `actor_hash(a) = sha256(canon({account, profiles_row, identities_rows_sorted_by(provider,subject), email_credential{email_norm,sha256(salt),sha256(password_hash),created,verified_at}, profile_save{revision,sha256(payload),updated}, sessions_count_and_hashset, receipts_sorted_by(store:transactionId) with crowns/refunded/at, journal_rows_for_actor (ORDER PRESERVED), matches_participating_with_role_and_escrow_share, rooms_participating_with_contribution, v35_rows_sorted, reports/privacy/deletion rows}))`.
- **Order versus set**: arrays whose order is meaningful (journal, history, ledger, moves, fixture history, payouts, net, ready, contributions, seasonHistory, boosts, fixture players) are hashed order-preserving; arrays that are semantically sets (friends, friendRequests, blocked, owned, redeemed, opponents, accepted, claimed, seen) are hashed both order-preserving and sorted, and the gate requires *set* equality always plus order equality for the closed order-meaningful list. A pure ordering difference in a set-array is recorded as explained category `array-order-normalized`, never as content equality.

## 2. V5-03-02 - Pure reader layer and complete hazard avoidance

### 2.1 Reader construction (IMPLEMENTED)

- Open the snapshot with `new DatabaseSync(file,{readOnly:true})` only. Never execute a statement that persists: `PRAGMA journal_mode` is a persisted database property and MUST NOT be set (contrast `server/economy-store.js:12`, `server/rooms.js:10`); connection-scoped pragmas (`busy_timeout`, `foreign_keys`) do not modify the file and are permitted but unnecessary.
- Read `state(id=1).json`, `party_rooms.json`, `party_commands`, `commands`, `social_operations`, `v35_commands` and every other durable table with a strict JSON reader (`parseStrictJson` in `tools/v5-migration/canonical.js`), never `JSON.parse`. Entry-array roots (`accounts`, `matches`, `receipts`, `snapshots`, `weeklyPaid`) and the nested `matches[i][1].commands` entry array and `party_rooms.players/groups/fixtures` are parsed as `[key, value]` pairs; object roots (`operations`, `daily`, `monetization.daily`) are parsed as plain objects.

  **IMPLEMENTED.** Duplicate JSON keys are detected before any value can be overwritten: the scanner tracks the key set per object and fails with `JSON_DUPLICATE_KEY` (a `JSON.parse` reviver cannot see a repeated key because the first value is already gone). `__proto__`/`constructor`/`prototype` keys are NOT rejected: they are legitimate source data (conversion operation keys, snapshot/audit payloads) and are preserved as own enumerable data properties via `Object.defineProperty`, so the parsed object's prototype is never reassigned and no prototype pollution occurs. Source-keyed hash dictionaries (`stateRoots.*.byKey`, `hashes.actorHashes`) use null-prototype objects and the same own-property write, so an actor or root id named `__proto__` is neither dropped nor polluting. Duplicate detection applies to those keys unchanged. Raw JSON text is preserved alongside the parsed value in `state.raw` and `rooms[].raw`, and an opaque payload's exact text is authoritative.
- **IMPLEMENTED.** The reader module's require graph contains none of: `src/authority.js`, `server/economy-store.js`, `server/community-store.js`, `server/rooms.js`, `server/monetization-store.js`, `server/store-bindings.js`, `server/jobs.js`, `server/community-server.js`, `server/party-server.js`, `server/production/{main,perimeter,read-context,mail-outbox,email-auth,operator-service,passwords}.js`, `server/matchmaking.js`, `server/queue-session.js`, `server/competitive-abuse.js`, `packages/domain`, or the P01 `createSqliteUnitOfWork` (which is a SQLite unit of work, explicitly not an import path: `local://v5-phase01-contract.md` states "extraction/import NEVER uses constructors" and "No constructor/migration/import magic in the new repositories"). `reader.js` depends only on `node:fs`, `node:path`, `node:crypto`, `node:sqlite`, `./canonical.js`, `./mapping.json`, and (for source-schema checksums) the frozen `server/production/migrations.js` array of pure checksum inputs. The reader opens exactly one `DatabaseSync` handle and closes it; it issues no statement that persists (no `PRAGMA journal_mode` write).

Rows whose id starts `mail-budget:` are the durable monthly email spend counter (`server/production/mail-outbox.js:37,44`) and must be migrated verbatim, never reset, so a budget is not silently replenished. Rows under the `abuse:` prefix (`server/production/abuse-guard.js`) are ephemeral rate buckets. `mapping.json` classifies `v4_limits` as disposition **V** (verbatim) and records the prefix split; the reader copies every row and the importer splits them per row by prefix.
  - `account_sessions` are expired by explicit planned policy, not because a stored token is intrinsically unrecoverable. The `token` column is already `sha256(token)` base64url (`server/identity-provider.js:12`), so a raw bearer token was never persisted; session continuity/compatibility is a P05 decision, still gated, and P03 makes no claim about it.
  - The reader reports each ephemeral table as a count plus content hash plus recorded policy in `coverage.tables[].disposition`; it never re-issues, upgrades, refreshes or extends such a row.

## 3. Determinism contract

### 3.1 Canonical serializer (IMPLEMENTED)

- Objects: keys sorted by UTF-16 code unit order; serialized as `{k:v,...}` with no whitespace; duplicate keys rejected; `undefined` rejected.
- Arrays: order preserved by default; set-valued arrays additionally hashed sorted (section 1.3).
- Strings: `JSON.stringify` (JSON escaping only; no Unicode normalization).
- Numbers: classified currency/ids/counters require `Number.isSafeInteger`; a value failing it is an error, never silently rounded. Fractional source numbers are preserved as exact JSON values — the design's original "closed hundredths allowlist" was too narrow and is superseded by the implemented per-field mapping kinds (`num` for any finite value, `hundredths` only where the source stores units/100, `ms` for finite non-negative epoch milliseconds). Two concrete **SOURCE CORRECTIONS**: `daily[date].seconds` is fractional (`Math.min(900,(now-started)/1000)`), and `receipt.rating.expectedA` is the raw `1/(1+10**((b-a)/400))` probability, not a hundredths value. `NaN`, `Infinity`, `-0`, unsafe integers and BigInt are errors, never silently rounded (`specs/01` section 3).

  **IMPLEMENTED — opaque TEXT metadata.** Opaque TEXT payloads (the practice archive, command/notification responses, operator audit `detail`) are the source's own legacy metadata, not classified money. They are syntax- and duplicate-scanned without asset-number semantics, so a legitimate legacy integral value beyond the safe range (e.g. a practice archive's `legacy.importedTicks = 1e20`) is accepted, its exact raw text stays authoritative, and each accepted path is recorded in `hashes.opaqueUnsafeNumbers`. Classified money/counter columns (`uint`/`int`/`ms`/`hundredths`) keep the strict safe-integer rule.
- Booleans/null literal. No re-serialization through `structuredClone` (which would silently drop `undefined` and reorder nothing but normalizes class instances) is used on raw text.

### 3.2 Stable IDs preserved verbatim (IMPLEMENTED)

- Actor/match/operation ids keep their exact text. The source's own validity grammar is reused for validation, not for rewriting: `validId=/^[A-Za-z0-9][A-Za-z0-9:_-]{0,159}$/` (`src/authority.js:6`), store/binding key grammar `/^[A-Za-z0-9:_-]{1,160}$/` (`server/monetization-store.js:5`, `server/community-store.js:34`), community mutation key grammar in `server/community-http.js:7`.
- Non-UUID actor ids (e.g. `u_<uuid>`, `p0..p11` in fixtures, or arbitrary legacy text) are stored as `text`, never cast to UUID (`specs/01` section 1).
- Tags (`MEGA-XXXXXXXX`) are never regenerated; `profiles.tag` and `accounts.friendCode` are copied verbatim and their equality/inconsistency is reconciled explicitly (the source writes `account.friendCode = tag` in `ensureProfile`, so a mismatch is a real historical variant, not a fixable inconsistency).
- Emails: preserve the stored value verbatim plus a normalized lowercase key; report collisions under PostgreSQL's case-insensitive uniqueness equivalent (`specs/01` section 1; source column is `COLLATE NOCASE`, VERIFIED DDL). Identities are never merged by email.
- Store bindings: `google_id`/`apple_token` copied byte-for-byte (contrast `server/store-bindings.js:6-16`, which mints them on first read).

### 3.3 Fixed clock injection (IMPLEMENTED)

- The single clock is the capture clock `captureClockMs = snapshot manifest.createdAt` (VERIFIED field; for `f884e43b` it is 1791396595015). The restic `snapshot_completed_at` (1791396602150) is recorded as provenance but not used as the semantic clock, because the manifest is created before the file is renamed into place by `snapshot()` (`server/production/backup.js:17-29`).
- Every derived classification ("is this OFFERED match expired at capture", "is this ticket settled/expired", "is this boost active", "which week/quarter does this journal row belong to", "is this season id the current quarter") is computed with `captureClockMs`, never `Date.now()`. Derived values are never written into raw-copy fields; they are recorded in the reconciler's derived report with `asOf = captureClockMs`.
- Cross-run determinism therefore requires equal `captureClockMs`; a run with a different clock must record the reason and any classification differences become explained-category `clock-different` rows, not silent passes.

### 3.4 Versioned extractor release hash (DESIGN)

`extractor_release = sha256(canon({extractorVersion, canonicalizerSpec, normalizationTables, mappingManifest, reconciliationRules, sourceRelease:{source_sha, running_image_digest, installed_script_hashes}}))`. The source-side provenance values are taken from the existing evidence (`docs/v5/evidence/phase00-live-operations.json` observations; baseline `455b8ec9ea4070b4410d78f9eea2aaa06d32c0b2` per `docs/v5/BASELINE.md`). Any change to a mapping row, a normalization disposition or a reconciliation rule changes `extractor_release` and therefore the run identity; a reused run id with a different release is refused (section 3.5).

### 3.5 Idempotence, ledger and interrupted-batch recovery (DESIGN)

PostgreSQL migration namespace `v5_migration`, owned by the migration role, created by the P02 checksummed migration chain (runtime roles cannot DDL, `docs/v5/ARCHITECTURE.md` item 7):

- `run(run_id, source_fingerprint, extractor_release, target_environment_id, schema_head, lock_token, lease_until, status, started_at, finished_at, counters)` where `source_fingerprint = sha256(canon({snapshot_id,file_sha256,bytes,captureClockMs,table_hashes,state_root_hashes,actor_hashes_root}))`.
- `target_guard(target_system_id, target_database, environment_id, schema_head, created_by_run, adopted_existing_tables[])` - one row; mismatch is a hard refusal.
- `batch(run_id, ordinal, kind, definition_hash, key_range_low, key_range_high, status, cursor, committed_row_hash, rows_written, attempt_count, error_code)` with a unique `(run_id, ordinal, definition_hash)`.
- `row_ledger(run_id, source_locator, target_table, target_pk_hash, row_hash, batch_ordinal)` unique on `(run_id, source_locator)`.
- `operation_outcome(run_id, family, op_id_hash, source_fingerprint_hash, response_hash, replay_class, replay_semantics)`.
- `coverage(run_id, locator_kind, name, key, classification, rule_id, note)`.
- `difference(run_id, category, actor_hash, locator, field_path, expected_hash, actual_hash, rule_id, severity)`.

Rules (DESIGN, each mapping to a normative requirement):

1. Refuse an unknown target: `target_guard` absent is *not* an implicit "create"; a target must be declared (nonserving, explicitly identified), and the guard binds `system_identifier`-equivalent identity, database name and environment id (`specs/01` section 2 "require an explicit environment ID ... refuse an unknown target").
2. Refuse a reused run id with a different `source_fingerprint` or `extractor_release` (`specs/01` section 2 "Refuse ... a reused run with a different source hash").
3. Refuse an active production writer: an allowlist of target databases plus a check that no non-namespace table has rows created after `run.started_at` by a foreign `created_by_run` (and no `pg_stat_activity` session with the production application name while the import transaction is open) (`specs/01` section 2).
4. Advisory lock on a **direct** (non-pooled) TLS connection: session-level `pg_advisory_lock` keyed by `hashtext('v5-migration:'||run_id)`, held for the run; the design must not assume session locks on transaction pooling (`docs/v5/ARCHITECTURE.md` item 8; P02-04 owns the connection policy).
5. Batching: fixed `batchSize` (default 500) with a deterministic total order per kind (sorted canonical source key), and cursors expressed as the last committed canonical key, never an offset, so a resumed run re-derives exactly the same row set; `definition_hash = sha256(canon({kind, source_locator, filter, order_by, batchSize}))`.
6. Write pattern: `INSERT ... ON CONFLICT (<stable target key>) DO NOTHING` followed by a hash comparison against the existing row; each batch commits in its own transaction (`specs/01` section 5 "deterministic batches with recorded checkpoints"); no unbounded single transaction.
7. Resume: `committed` batches verify `row_ledger` hashes against the target and are skipped; `running` with a stale lease is re-executed (PostgreSQL aborts the interrupted transaction on disconnect); `failed` is re-executed after `attempt_count` is incremented; a hash mismatch on a previously committed row is a hard failure, never an overwrite.
8. No destructive operations on anything not created by this run: `TRUNCATE`/`DROP` require `created_by_run = run_id` and an explicit `--confirm-destroy=<schema>` and are refused for any other object (`pack phases/03`: "never truncate an unknown database").
9. Rerun convergence is asserted, not assumed: `load` twice (and once after killing the process between batches in each kind) must produce identical `run.counters`, identical `state_root_hashes`, identical `actor_hashes_root` and identical `row_ledger` hashes (`pack phases/03` V5-03-05 verification).

### 3.6 Proofs that a rerun never mints or re-grants

Each proof is an executed assertion in the rerun test; the invariants are quoted from `specs/01`:

- "Duplicate settlement, callback, import or retry adds no extra posting or entitlement" (section 4) - proven by: journal row count and per-actor `opening:` count unchanged across two runs; `receipts` key set and `refunded` flags unchanged; `v35_tickets.settled`/`transaction_id` unchanged; `v41_store_bindings` byte-identical.
- "Reserved holdings and escrow are two representations of the same encumbrance" (section 4) - proven by the reserved-closure equation R2 (section 4.3) holding on both runs with identical residuals.
- "Import historical entries with immutable source references; do not replay them against balances that were already loaded" (section 4) - proven by: legacy journal postings are inserted as `origin='legacy-journal'` rows only, never as balance-affecting postings; the only balance-bearing row per actor/currency is the labeled `origin='migration-opening-balance'` baseline, whose amount equals the captured available+reserved encumbrance total and whose count is exactly one per actor/currency.
- "Migration twice must produce equivalent canonical state and the same source mapping" (section 5) and "no repeated batch can mint funds or duplicate identity/purchase records" (section 5) - proven by the byte-identical canonical target hash across reruns and across interrupted-batch recovery, plus zero new rows in identity/purchase/entitlement tables on the second run.
- Conservation equations C1-C9 (section 4.3) hold exactly (no tolerance) on the first import and identically on every rerun.

### 4.2 Per-actor currency totals (DESIGN)

For each actor `a` and currency `c`: `available_c(a) = a.coins | a.crowns`, `reserved_c(a) = a.reservedCoins | a.reservedCrowns`, `purchased_c(a) = a.purchasedCoins | a.purchasedCrowns`, `credits(a) = a.monetization.credits`, `owned(a)`, `equipped(a)`, active/expired `boosts` at `captureClockMs`. ### 4.3 Conservation equations (each asserted exactly; source citations)

- **C1 available/reserved identity**: `target.available_c(a) == source.available_c(a)` and `target.reserved_c(a) == source.reserved_c(a)` (`specs/01` section 4; `src/authority.js:24` field set).
- **C2 reserved-closure**: for each `a,c`: `reserved_c(a) == Σ_{m open} contribution_m(a) + Σ_{r open} contribution_r(a)` where "open" = `escrow > 0 && !settled`; match contributions are `m.quote.contributions[i]` indexed by `m.players` position with currency `m.quote.currency` (`src/authority.js` accept: `m.escrow = m.quote.pool` and both players' `held` incremented; the earlier `D.add` loop is a pure safe-integer preflight, not a mutation, VERIFIED `src/domain.js:19`); room contributions are `r.contributions[{id,amount}]` with `r.escrow = q.pool` (`server/rooms.js` reserve). Residual must be exactly 0 (`specs/01` section 4 "Separately reconcile each escrow and its contributions to the reserved total").

- **C3 burn composition**: `state.burned[c] == Σ settled match receipt.burn + Σ settled room receipt.burn`. This is deliberately *not* `-Σ journal{reason='Currency retired'}`: match burns are journaled under actor `system` with reason `Currency retired` (`src/authority.js` `_settle`), while tournament burns update `e.burned[c]` with **no** journal row (`server/rooms.js` settle). The journal-based subset is reported as a distribution, never used as the balance equation - this is the concrete "do not double count" rule required by A09 and `specs/01` section 4.
- **C4 conversion fidelity**: for every conversion operation key, exactly two `account.ledger` rows (`<key>:out`, `<key>:in`) and exactly two journal rows with `source='conversion'`; the 10:1 rule re-checked with the pure `D.conversion` (`src/domain.js:72-76`) and `amount % coinsPerCrown == 0` for Coin->Crown. No repricing (`docs/v5/ROUTE-AND-DATA-INVENTORY.md` section 3 "Extract function output verbatim; no repricing").
- **C5 tournament pool algebra**: per public table `pool == entry*10`, `burn == pool/10`, `Σ payouts + burn == pool`, `payouts[4] == entry` (VERIFIED `tests/design-invariants.test.js:29-31`; `src/tournament.js:4-9`).
- **C6 wealth identity**: `D.wealth(w) == coins + reservedCoins + (crowns + reservedCrowns)*10` with held counted once (`src/domain.js:77`); computed for both sides only as a cross-check, never as a substitute for C1/C2.
- **C7 occupancy single-valued**: each `a.activeMatch` is `null`, a match id, or `'tournament:'+roomId` (`server/rooms.js` reserve); for every `OFFERED`/`PLAYING` match, both players' `activeMatch` equal that match id; for every room with reservations, contributors' `activeMatch` equal `'tournament:'+roomId`. Reverse map must be injective.
- **C8 relationship symmetry**: `friends` symmetric in both directions; `friendRequests` directional; `blocked` directional; the four cleanup actions (`remove`, `block`, `decline`, `cancel`) must have left the documented residual state (`server/community-store.js` social).
- **C9 tombstone/principal referential classes**: every id referenced from `matches.players`, `matches.accepted`, `matches.symbols`, `room.players`, `room.ranking`, `room.contributions`, `history[].opponent`, `season.opponents`, `seasonHistory[].opponents`, `weeklyPaid`, `snapshots`, `journal.actor` resolves to (i) an existing source account id, (ii) a `deleted_<uuid>` tombstone produced by deletion (`server/community-store.js` `deleteAccount`), or (iii) a LAN guest actor present in `party_guests` (quarantined, never materialized as a platform actor). Any other unresolvable reference is an unexplained difference.

The reader does not depend on `packages/domain`; only the reconciliation validators (unimplemented) may import pure `src/domain.js` functions (`day/week/season/wealth/conversion/elo`) and only behind an injected clock.

Open design questions the parent should decide explicitly before implementation: (a) whether imported `v4_outbox` rows are migrated as inert rows or recorded as drained (both are permitted; the choice must be recorded in the mapping manifest); (b) whether `account_sessions` are imported as forensic revoked rows or only counted (the token column is already a hash, so either is safe, but the choice affects the A12/P05 session-continuity design); (c) whether the `matches[].commands` RECOMPUTABLE probe stays RECOMPUTABLE after the first fixture run or degrades to OPAQUE_VERBATIM (the decision must be data-driven from the fixture and recorded, never guessed); (d) whether the A07 swapped-wallet fixture lives in the P03 suite or is shared with P04's differential suite (P04 re-runs A07 per `acceptance.json`).

The require-graph purity property is stated as an implemented fact for the current `reader.js` module graph, not asserted by a text/import-graph test; a future transitive import is a review concern for the module's own reviewers.
